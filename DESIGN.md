## Brand

- Personality: quiet, compact, utilitarian, and trustworthy.
- Trust signals: persistent local data, explicit auto/manual state, immediate feedback, and reversible UI actions.
- Avoid: oversized controls, developer-facing implementation details, decorative clutter, and explanatory copy that competes with the primary task.

## Product goals

- Goals: make daily focus and habit state fast to scan and change; preserve manual control over automation.
- Non-goals: mobile-first layouts, public accounts, social features, or a general project-management system.
- Success signals: common actions require one click or direct manipulation; users do not need database/API vocabulary.

## Personas and jobs

- Primary personas: the local owner of the dashboard and external automation agents.
- User jobs: review recent activity, toggle habit completion, configure habits, and rank them by personal importance.
- Key contexts of use: a desktop browser during daily review and background API/SQL automation.

## Information architecture

- Primary navigation: Today, Habits, Calendar, Database, Settings.
- Core routes/screens: `/habits` is the second tab and the habit-management surface.
- Content hierarchy: date range and legend, four-week grid, ordered habit rows, then secondary edit/archive actions.

## Design principles

- Hide system internals: stable integration IDs are generated by the server and are not editable form fields.
- Prefer direct manipulation: habit priority is changed with a visible drag handle; keyboard arrows provide the same operation.
- Keep row actions compact: use icon-only add/edit/archive controls with accessible labels and tooltips.
- Preserve user authority: manual habit state always wins over automatic updates.
- Tradeoffs: stable text IDs remain in storage/API for integration compatibility even though the UI does not expose them.

## Visual language

- Color: existing dark neutral palette; green for done, cyan for current/auto accents, red only for destructive actions.
- Typography: existing Inter/system stack, compact labels, muted secondary metadata.
- Spacing/layout rhythm: 4 px base rhythm; row controls should not increase the grid row height unnecessarily.
- Shape/radius/elevation: existing 6 px radius and restrained borders/shadows.
- Motion: short state transitions only; drag feedback uses opacity, border, and insertion indicators.
- Imagery/iconography: Lucide icons already used by the application.

## Components

- Existing components to reuse: shadcn Button, Dialog, AlertDialog, Input, Label, Switch, and Tooltip.
- New/changed components: habit reorder grip and drag insertion state inside `Habits.tsx`.
- Variants and states: idle, keyboard focused, dragging, drop-before, drop-after, saving, error, and disabled.
- Token/component ownership: use the existing Tailwind theme; do not introduce a parallel design-token layer.

## Accessibility

- Target standard: practical WCAG 2.1 AA behavior for the local desktop surface.
- Keyboard/focus behavior: the reorder grip is focusable; ArrowUp/ArrowDown moves a habit and announces position through its accessible label.
- Contrast/readability: reuse established foreground/muted/destructive colors.
- Screen-reader semantics: icon-only controls require specific `aria-label`; stable IDs remain hidden because they are not user decisions.
- Reduced motion and sensory considerations: ordering must not depend on animation or color alone.

## Responsive behavior

- Supported breakpoints/devices: desktop browser; the four-week grid may scroll horizontally on narrow windows.
- Layout adaptations: preserve the fixed minimum grid width and compact first column.
- Touch/hover differences: HTML drag-and-drop is desktop-oriented; keyboard ordering remains available without hover.

## Interaction states

- Loading: preserve the current row-area loading message.
- Empty: the add icon remains visible when no active habits exist.
- Error: failed reorder rolls back the optimistic order and shows an inline error.
- Success: order updates immediately and persists after reload.
- Disabled: block concurrent reorder requests and future-day cell toggles.
- Offline/slow network: optimistic reorder and cell updates roll back on failure.

## Content voice

- Tone: brief, direct, and user-facing.
- Terminology: “activity” in editor actions, “habit” in the grid; never ask the user for a primary key or slug.
- Microcopy rules: explain automation effects, not storage implementation.

## Implementation constraints

- Framework/styling system: React, TanStack Query, Tailwind v4, shadcn/ui, Express, Drizzle, SQLite.
- Design-token constraints: reuse existing CSS variables and Lucide icons.
- Performance constraints: reorder one short active-definition list in a short SQLite transaction.
- Compatibility constraints: existing habit IDs and external autofill integrations must remain valid.
- Test/screenshot expectations: pure reorder helper tests, API ordering/validation tests, typecheck, build, and live `/habits` smoke verification.
